# CONTRIBUTING

Спасибо, что хотите поучаствовать в проекте **Highload Filehost + Rust EdgeCache**.

Этот документ описывает единые правила для:
- ведения задач (issues),
- веток, коммитов и Pull Request,
- качества кода, тестов и документации,
- Definition of Done.

> Язык команды и артефактов по умолчанию: **русский** (issues, документация, обсуждения PR, README).

---

## 1) Где лежит документация

- **Wiki (основная документация):** https://github.com/OlegDokuchaev/highload-filehost-edgecache/wiki
- **README (быстрый старт):** `README.md`

При создании/обновлении тикетов и PR **обязательно** добавляйте ссылку на раздел документации/ТЗ, если это возможно.

---

## 2) Как запустить проект локально

Минимальный запуск:
```bash
docker compose up -d --build
````

Проверка сервисов (пример):

* Users: `http://localhost:<users_port>/docs`
* Origin: `http://localhost:<origin_port>/docs`
* EdgeCache: `http://localhost:<edge_port>/healthz`

## 3) Issue-трекер: требования к тикетам (GitHub Issues)

Каждый тикет должен содержать:

1. **Краткое название**: что делаем (1 строка)
2. **Описание**: что должно получиться (ожидаемое поведение/изменение)
3. **Acceptance Criteria**: как понять, что готово (чеклист)
4. **Оценка**: story points
5. **Ссылка на ТЗ/документацию**: раздел Wiki/docs (если применимо)

Рекомендуемый шаблон:

```md
## Что делаем
Коротко опишите цель.

## Контекст / ссылка на ТЗ
- Раздел документации: ...

## Acceptance Criteria
- [ ] ...
- [ ] ...
- [ ] ...

## Оценка
SP: ...

## Примечания
(опционально) ограничения/риски/особые условия
```

## 4) Git: модель веток и PR

### Ветки

* `main` — защищённая ветка (всё только через PR).
* Вся работа — через feature-ветки.

Рекомендованный формат имени ветки:

* `feat/PROJ-12-auth`
* `fix/PROJ-34-cache-bug`
* `refactor/PROJ-56-edgecache-io`
* `docs/PROJ-78-update-tz`

> `PROJ-12` — номер тикета (issue). Если тикетов пока нет, используйте `NOISSUE` временно, но лучше завести тикет.

### Pull Request

Требования к PR:

* PR связан с тикетом: `Closes #123` / `Fixes #123` в описании PR.
* Минимум **1 approval** от другого участника команды.
* CI должен быть зелёным до merge.
* Любое изменение в `main` — только через PR.

---

## 5) Commit message (Conventional Commits)

Используем Conventional Commits:

* `feat: ...` — новая фича
* `fix: ...` — исправление бага
* `refactor: ...` — рефакторинг без изменения поведения
* `perf: ...` — улучшение производительности
* `test: ...` — тесты
* `docs: ...` — документация
* `chore: ...` — инфраструктура/скрипты/рутина

Рекомендуемый формат:

```
<type>(<scope>): <summary> [#issue]
```

Примеры:

* `feat(edgecache): добавлен request coalescing #12`
* `fix(origin): исправлена выдача корректного ETag #34`
* `docs(wiki): обновлены шаги деплоя #78`

---

## 6) Требования к качеству кода

* Изменения должны быть минимальными и понятными.
* Избегайте скрытых сайд-эффектов и “магии”.
* Логи — информативные (без спама), ошибки — с контекстом.

---

## 7) Тестирование (минимум)

Минимум:

* unit-тесты на ключевую бизнес-логику (если применимо).

Желательно:

* 1 интеграционный тест на основной сценарий (API/БД/кэш),
* e2e тест для пользовательского сценария (upload → download через edgecache).

Если вы меняете поведение API/кэша — добавьте/обновите тесты и документацию.

---

## 8) Документация (обязательна при изменениях)

Документацию нужно обновлять, если вы:

* меняете требования/поведение,
* меняете архитектуру (компоненты, взаимодействия),
* добавляете/меняете API,
* меняете деплой/окружение/порты/переменные окружения,
* меняете правила кеширования, метрики, нагрузочное тестирование.

Где обновлять:

* Wiki (основной источник)

---

## 9) Definition of Done (DoD)

Задача считается выполненной, если:

* [ ] Код написан и покрыт тестами
* [ ] PR создан и прошёл code review
* [ ] CI успешно прошёл
* [ ] Документация обновлена (если менялись требования/архитектура/контракты)
* [ ] Тикет закрыт и связан с PR/коммитами
* [ ] Изменение попало в `main` через PR

---

## 10) Что делать, если не уверены

Если вы не уверены:

* заведите issue с вопросом/предложением,
* приложите ссылку на раздел Wiki/ТЗ,
* опишите варианты и риски.

Лучше маленький прозрачный шаг, чем “большой коммит без контекста”.
